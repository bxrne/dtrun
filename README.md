# dtrun

Deterministic execution for OCI containers.

`dtrun` is an experimental container runtime designed to make container execution reproducible by controlling the sources of nondeterminism exposed to the workload.

It is intended to provide the deterministic execution backend for [dstest](https://github.com/bxrne/dstest) which  can deterministically generate a workload and fault scenario, but the container itself still executes under a normal Linux environment. `dtrun` explores the other half of the problem: making execution itself reproducible.

## Why?

Normal container execution leaves a large amount of behaviour to the host:

* thread scheduling
* wall-clock time
* randomness
* network ordering
* I/O completion
* resource availability

```text
                 dstest
                    │
          workload + faults
                    │
              ┌─────┴─────┐
              │            │
           Docker        dtrun
              │            │
        real execution   deterministic
                         execution
```

The goal is not to require applications to be rewritten for simulation. An OCI image should remain the unit of deployment.

## Goals

* Execute existing OCI images without application instrumentation.
* Provide deterministic virtual time.
* Provide deterministic randomness.
* Control scheduling and event ordering.
* Provide deterministic network behaviour.
* Provide deterministic storage/I/O behaviour.
* Record executions for replay.
* Reproduce failures from a seed and execution trace.

## Non-goals

`dtrun` is not intended to:

* replace Docker or containerd as a general-purpose runtime.
* provide production container isolation.
* emulate an entire operating system.
* guarantee deterministic behaviour without controlling the relevant sources of nondeterminism.

## Plan

1. Parse the OCI Container Bundle
    When dtrun is invoked by Docker or dstest, it reads the container's config.json to extract the entrypoint command, arguments, environment variables, and the path to the root filesystem (rootfs).
2. Isolate the Host using Linux Namespaces
    We unshare and create new Linux namespaces for Process IDs (PID), Mount points, Hostname (UTS), and IPC. This prevents the container process from seeing or interacting with the host system directly.
3. Isolate the Filesystem
    We switch the execution root (chroot or pivot_root) into the container's rootfs directory so the container binary only sees its own internal files and libraries.
4. Attach the System Call Interceptor
    Before launching the container's PID 1 process, we declare ptrace tracing (PTRACE_TRACEME). This tells the Linux kernel to stop the process every time it tries to perform an action that interacts with the hardware or kernel.
5. Start the Main Event Loop
    The parent dtrun process enters a monitoring loop (waitpid), keeping the container process paused at every system call boundary (entry and exit).
6. Trap Sources of Non-Determinism
    Every time the container requests external data, dtrun inspects the active CPU registers to see which system call is being made:
    a. Randomness (getrandom): We intercept the call, overwrite the destination memory buffer directly via /proc/<pid>/mem with seed-generated bytes, and skip the real kernel logic.
    b. Time (clock_gettime, gettimeofday): We catch time requests and replace host timestamps with a fixed or incrementally advancing virtual clock.
7. Control Thread Scheduling
    When the process calls clone or clone3 to spawn threads, dtrun catches the event, registers the new Thread ID, and manually pauses/resumes threads so that only one thread executes at a time in a deterministic order.
8. Log the Execution Event Trace
    For every intercepted event, dtrun writes a sequential log containing the event type, seed state, and injected outputs so the exact run can be audited or replayed later.
9. Collect the Exit Status
    When the container's PID 1 terminates, dtrun catches the exit signal, cleans up child process state, and forwards the final exit code back to the caller.
